# Downstream Setup Automation — Prompt Sequence

**Status:** working artifact, not part of the consumer documentation set. It turns a seven-iteration plan into prompts you can paste into a fresh session. Delete this file once the work has landed and `CHANGELOG.md` carries the history.

## The problem this solves

A repository created from this template inherits the template's own scaffolding, and several contract tests actively require it. Standing up a real bot from this template meant fighting:

1. **The six AI instruction files.** Three `mv` commands by hand, and `test/contracts/instructions.test.js` fails a half-finished swap. After a correct swap, that test plus `test/helpers/instruction-files.js` is ~320 lines whose only surviving downstream assertion is "no version line remains."
2. **`.dev.vars.example` is mandatory.** `test/contracts/discord.test.js` requires it to exist, be tracked, name every secret in `secrets.required` plus `DISCORD_GUILD_ID`, and contain *nothing but* `replace-me` values. It cannot be deleted and cannot hold a real value.
3. **The MCP server set is pinned exactly** — `test/contracts/workflow.test.js` asserts exactly three servers at exact URLs with exactly the keys `type` and `url`. Adding or dropping one downstream fails `npm test`.
4. **The environment list is pinned exactly** — `test/contracts/discord.test.js` asserts `Object.keys(config.env).sort()` equals `["non-prod","production"]`. A third environment breaks it.
5. **Coverage thresholds are 100%** across `src/**` and `scripts/lib/**` in `vitest.config.js`. Correct for a template with three commands; in an application repo the first partially-covered feature fails `npm test`, and `claude.md` forbids lowering it.
6. **Inherited template state** — eleven unreleased changesets in `.changeset/`, the template's `CHANGELOG.md`, a maintainer-facing `CONTRIBUTING.md`, a 591-line setup guide, and a 235-line README that is mostly template quickstart.

The fix is `npm run setup`: one command, run once in a fresh project, that prunes the template's scaffolding, renames the project, and deletes itself.

## Decisions already made

These are settled. A session executing a prompt below should not re-litigate them.

| Decision | Choice |
| --- | --- |
| Script scope | Local files only, plus a separate opt-in `npm run setup:github` |
| `.dev.vars.example` | Script copies it to `.dev.vars`, then deletes the example and its contract test |
| Coverage ratchet downstream | Lowered to a floor — **80** across all four metrics (confirm this number before Iteration 3) |
| Script lifetime | `npm run setup` deletes itself, its lib, its tests, and its npm script as its last act |
| `setup:github` lifetime | Permanent — re-running it re-verifies GitHub settings |
| Template-only test blocks | Split into their own files upstream first, so the script only ever deletes whole files |
| `setup:github` and secrets | Creates environments, the `DEPLOY_ENABLED` variable, and the ruleset; never sets a secret value. Verifies which secret *names* exist and reports what is missing |
| `LICENSE.md` and `package.json` author | Left alone, with a clear warning printed |
| Release classification | Minor package bump, instruction contract **3.1.0**. No upstream promise is removed — the template keeps its own template-only tests; the script prunes them from the copy |

## Two design choices not to undo

**Template-only tests are named, not foldered.** They go in `test/contracts/*.template-only.test.js`, beside their siblings — not in a `test/contracts/template-only/` subdirectory. A subdirectory forces `test:contracts` to either recurse (`node --test test/contracts/`, whose default patterns also match non-test `.js` files under a directory named `test`) or carry a second glob that errors once the script deletes the directory. The filename suffix is matched by the existing `test/contracts/*.test.js` glob, needs no `package.json` change, and makes pruning file-level.

**Downstream prose is shipped as files, not generated by code.** A `.template/` directory holds the downstream replacements for the documents that are written from the template's point of view (`README.md`, `docs/using-ai.md`, `docs/using-this-template.md`), with `{{PLACEHOLDER}}` tokens the script substitutes. Prose does not belong in JavaScript string literals, and section-surgery on Markdown by regex is the part most likely to break on a future upstream edit. Only the three documents whose *entire* framing is template-specific get a shipped replacement; the rest are handled by link rewriting.

## The link fallout (the least obvious part)

Pruning `docs/using-this-template.md` and `CONTRIBUTING.md` breaks eleven links in documents that survive:

| File | Lines | Points at |
| --- | --- | --- |
| `docs/discord-bot.md` | 3, 121, 139, 158, 281, 291 | `using-this-template.md` and five of its anchors |
| `docs/gitflow-and-branching.md` | 3, 95 | `using-this-template.md#6-configure-branch-protection` |
| `docs/versioning-and-changesets.md` | 81, 95 | `../CONTRIBUTING.md#keeping-the-instruction-files-in-sync`, `using-this-template.md#10-keeping-up-with-upstream-changes` |
| `docs/using-ai.md` | 39 | `using-this-template.md#1-create-and-clone-your-repository` |

Handling, decided:

- `docs/using-this-template.md` is replaced by a short provenance stub from `.template/`, so the path still resolves.
- Relative links of the form `using-this-template.md#anchor` are rewritten to the upstream blob URL, which keeps the anchor accurate. One regex, fully testable.
- `docs/versioning-and-changesets.md` line 81's paragraph is **removed**, not re-linked: "keep the instruction contract version identical across all three instruction files" is meaningless in a project whose files carry no version. This is the one section removal in the plan.
- `docs/using-ai.md` gets a shipped replacement, because its "instruction files" table (lines 21–51) is written entirely from the maintainer's side.

## How to use this file

One iteration per session, one iteration per branch, one iteration per pull request. Paste the prompt block verbatim; each names the files and tests it touches, so it does not depend on conversation history.

This repository branches from and targets `main` — it has no `develop` branch and deploys nothing itself. Start each iteration with:

```sh
git switch main
git pull --ff-only
git switch -c feature/<iteration-branch-name>
```

`claude.md` is loaded automatically, so an assistant already has the maintenance contract, the TDD requirement, and the secrets rules. The standing rules below restate the few that are easiest to skip under momentum.

### Standing rules for every iteration

1. **Red before green.** Write the failing test first and *show it failing* before implementing.
2. **Smallest change that passes.** Then refactor while green.
3. **Green means green.** `npm test` and `npm run lint` both pass before the iteration is done. Never leave a failing check for a later iteration.
4. **Coverage never drops.** `scripts/lib/` is inside the 100% ratchet, so every new pure function needs full branch coverage in the same change.
5. **Docs land with the change.** A changed command, file layout, secret, or workflow changes its documentation in the same commit.
6. **Record a changeset** (`npm run changeset`) unless the iteration touches only Markdown.
7. **No secrets, ever** — including test fixtures and example files.
8. **Determinism.** No wall-clock or network dependence in tests. Inject a clock where a timestamp is written.
9. **Report what ran.** Name the commands executed and any check that could not run, and why.
10. **Do not commit or push unless asked.** Leave the work in the tree for review.

### Iteration map

| # | Delivers | Branch |
| --- | --- | --- |
| 0 | Pre-flight: a clean baseline and a released version to point provenance at | — |

## Iteration 1 — Split the template-only contract tests

**Delivers:** every assertion that is true only of this repository lives in a file the setup script can delete whole, and the assertions that ship downstream are relaxed to match the promise rather than this checkout. **Branch:** `feature/split-template-only-contract-tests`

```text
Read docs/downstream-setup-automation.md, sections "Decisions already made", "Two design choices
not to undo", and Iteration 1. Apply the standing rules in that file.

Establish the baseline first: `npm install` if node_modules is absent, then `npm test` and
`npm run lint`. Report the results and stop if either is not green.

Goal: separate the contract assertions that are true only of this template from the ones a
project built from it should keep. Nothing changes behavior; this is a move plus a relaxation.

Create these files, named with the `.template-only.test.js` suffix so the existing
`test/contracts/*.test.js` glob in the `test:contracts` script still matches them, and so the
setup script can later delete them file-by-file. Do NOT create a subdirectory — the reasoning is
in "Two design choices not to undo" and should not be revisited.

1. test/contracts/instructions.template-only.test.js
   Move test/contracts/instructions.test.js here unchanged. test/helpers/instruction-files.js
   stays where it is (it is pruned by path later, not by name).

2. test/contracts/discord.template-only.test.js
   Move from test/contracts/discord.test.js:
   - the whole `it("provides a placeholder-only .dev.vars.example covering every Discord
     variable")` case and the `devVarsExamplePath` constant it needs;
   - the exactness half of `it("covers both a non-production and a production environment")` —
     i.e. the assertion that the environment set is exactly ["non-prod","production"].

3. test/contracts/workflow.template-only.test.js
   Move from test/contracts/workflow.test.js the exact-value half of `it("declares the same MCP
   servers in both config formats without credentials")`: the three expected server names and
   their exact URLs.

Then relax what remains in the shipped files, so each still asserts a real promise:

- discord.test.js keeps a case asserting that BOTH a non-production and a production environment
  exist in wrangler.jsonc, without constraining the full set — a project may add a third.
- workflow.test.js keeps a case asserting that .mcp.json and .vscode/mcp.json declare the SAME
  set of server names (whatever it is), that every entry is `{ type: "http", url }` with no
  additional keys, and that no entry carries a credential-shaped key such as headers, token,
  apiKey, or env. That is the promise: the two files agree and neither holds a secret.
- discord.test.js keeps both .gitignore cases, including the `git check-ignore` one. Leave the
  `.dev.vars.example` assertion inside the check-ignore case alone: `git check-ignore` does not
  require the file to exist, so it still passes after the setup script deletes it.

Verify the split is honest by proving each relaxed case can still fail: temporarily break
wrangler.jsonc's env set to only non-prod, and temporarily add a `headers` key to one MCP server
entry, confirm the relaxed cases fail, then revert. Report that you did this — a guard nobody has
seen fail is not a guard.

Update CONTRIBUTING.md to describe the `.template-only.test.js` convention: what belongs in such
a file, and that a project created from this template deletes them.

Done when: npm test and npm run lint pass; `node --test test/contracts/*.test.js` runs all seven
contract files including the three new ones; no assertion was deleted outright (each one either
stayed, moved, or was replaced by a relaxed form covering the same promise); CONTRIBUTING.md
documents the convention; a changeset is recorded.
```

## Iteration 2 — The manifest and the payload

**Delivers:** what is template-only becomes reviewable data rather than logic buried in a script, and the downstream replacements for the three template-framed documents exist as files. **Branch:** `feature/template-manifest`

```text
Read docs/downstream-setup-automation.md, sections "Decisions already made", "Two design choices
not to undo", "The link fallout", and Iteration 2. Apply the standing rules in that file.

Baseline first: npm test and npm run lint. Report and stop if not green.

Deliver three things: a manifest, a payload directory, and a pure planner. No CLI yet, and
nothing in this iteration mutates the repository when run.

1. template-manifest.json at the repository root. Declarative, no logic. It needs to express:
   - prune: exact paths to delete. At minimum CONTRIBUTING.md, CHANGELOG.md,
     docs/using-this-template.md, docs/template-acceptance-test.md, docs/downstream-setup-
     automation.md, .dev.vars.example, template-manifest.json, the three
     test/contracts/*.template-only.test.js files, test/helpers/instruction-files.js, and the
     .template/ directory itself.
   - pruneGlobs: `.changeset/*.md` (config.json is not .md, so it survives without a keep list).
   - instructionFiles: the three maintainer paths and their three -for-users counterparts, as
     pairs, so the swap is data too.
   - copy: entries mapping a .template/ source to its destination.
   - selfDelete: scripts/setup.js, scripts/lib/setup.js, test/scripts/setup.test.js, and the
     `setup` key in package.json scripts.
   Choose the exact key names and shape yourself; keep it flat and obvious.

2. A .template/ directory holding the downstream replacements, with {{PLACEHOLDER}} tokens:
   - .template/README.md — a short project README: title from the project name, what it is (a
     one-line placeholder the project fills in), `npm install` / `npm run dev` / `npm test`, the
     everyday-commands content worth keeping from the current README.md lines 163-208, a
     deployment pointer, and links to the four surviving docs (discord-bot.md,
     gitflow-and-branching.md, versioning-and-changesets.md, using-ai.md). It must NOT link to
     using-this-template.md as a setup guide or mention "template quickstart".
   - .template/docs/using-ai.md — the same document rewritten for a project that has already
     swapped its instruction files: no maintainer/downstream table, no instruction contract
     version, no swap instructions. Keep the MCP section, "Documentation lookup is not
     authorization", "The guardrails that actually hold", "Working effectively", the secrets and
     permissions section, and "If you would rather not use AI". Reuse the prose; do not rewrite
     from scratch.
   - .template/docs/using-this-template.md — a ten-to-twenty-line provenance stub. It exists so
     the eleven inbound links in the surviving docs still resolve. It should say this project was
     created from {{TEMPLATE_REPOSITORY}} at {{TEMPLATE_VERSION}}, that setup is complete, and
     link to the full setup guide upstream.
   - .template/CHANGELOG.md — an empty stub for {{PROJECT_NAME}} with no entries.
   Placeholder names are yours to choose; document them in the manifest or alongside it.

3. scripts/lib/setup.js — pure functions only, no filesystem writes, no process.exit:
   - a planner that takes the parsed manifest plus a listing of the files present and returns an
     ordered plan of operations (copy, then prune, then self-delete last);
   - resolution of pruneGlobs against the listing;
   - the instruction-file decision: given "swap" or "delete", return the moves or deletions,
     and given a repository where the swap already happened, return nothing rather than failing.
   scripts/lib/ is inside the 100% coverage ratchet, so every branch needs a test.

4. A contract test — test/contracts/manifest.test.js, which SHIPS downstream, plus whatever
   belongs in a .template-only counterpart. Assert the promises:
   - every path in the manifest's prune and copy lists exists in this repository (a manifest that
     names a moved file is the failure mode that matters);
   - every .template/ file has exactly one copy destination, and every copy destination's parent
     directory exists;
   - every placeholder token appearing in a .template/ file is one the manifest declares, and
     every declared token is used by at least one file;
   - the six instruction files in the manifest match the six that exist;
   - no .template/ file and no manifest entry contains a credential-shaped literal (reuse the
     shapes already defined in test/contracts/discord.test.js rather than redefining them).
   Decide which of these are template-only and put those in the counterpart file, remembering
   that the manifest itself is pruned downstream — so the shipped test must tolerate its absence
   or must itself be template-only. State your reasoning in a comment.

5. Add test/scripts/setup.test.js for the planner, alongside the existing
   test/scripts/registration.test.js.

Done when: npm test and npm run lint pass; scripts/lib/setup.js is at 100% coverage without
lowering any threshold; the manifest names every file this plan prunes; nothing in this iteration
can modify a repository when imported; a changeset is recorded.
```

## Iteration 3 — Project-identity rewrites

**Delivers:** the pure transforms that turn this template's identity into a project's. **Branch:** `feature/setup-project-identity`

```text
Read docs/downstream-setup-automation.md, sections "Decisions already made", "The link fallout",
and Iteration 3. Apply the standing rules in that file. Confirm the coverage floor number (80) at
the start; do not proceed on that item if it is unconfirmed.

Baseline first: npm test and npm run lint. Report and stop if not green.

Extend scripts/lib/setup.js with pure transforms — each takes text or a parsed object in and
returns the new text or object, touching no filesystem. Test each against the real current
content of the file it targets, so a future upstream edit that breaks a transform fails loudly.

1. Slug validation and name derivation. Given a project slug, validate it against Cloudflare's
   Worker naming rules (lowercase letters, digits and dashes, no leading or trailing dash, 63
   characters or fewer, and leaving room for the longest suffix) and derive three names:
   the slug, `<slug>-non-prod`, and `<slug>-production`. The derived names must satisfy
   test/contracts/environment-isolation.test.js's naming assertions — assert that relationship
   directly in a test rather than assuming it.

2. wrangler.jsonc: replace exactly the three `name` values, leaving compatibility_date,
   observability, and every secrets.required block untouched. The file has no comments today but
   is named .jsonc — do not reformat it, and preserve byte-for-byte everything you are not
   changing.

3. package.json: set name and description from the project, drop the `template` and `boilerplate`
   keywords while keeping the Discord ones, reset version to 0.0.0, and remove the `setup` script
   key. Leave `author` and `license` alone — see the decision table. Preserve key order and the
   file's two-space formatting.

4. package-lock.json: update the two `name` occurrences (the root object and
   packages[""].name) and nothing else.

5. vitest.config.js: rewrite the four threshold numbers to the floor and replace the ratchet
   comment above them with wording appropriate to a project. Leave provider: "istanbul", leave
   thresholds.autoUpdate absent, and leave the coverage include patterns alone — the existing
   test/contracts/coverage.test.js assertions must still pass afterward, including that every
   threshold is greater than zero.

6. Placeholder substitution for the .template/ payload: replace every declared token, and fail
   loudly on an unsubstituted token remaining in the output rather than shipping a file
   containing {{PROJECT_NAME}}.

7. Link rewriting across the four surviving docs. Rewrite relative links of the form
   `using-this-template.md#<anchor>` (and the bare `using-this-template.md` where it is used as a
   setup-guide reference) to the upstream blob URL, preserving the anchor. The eleven affected
   locations are tabulated in "The link fallout"; assert the count so a future doc edit that adds
   a twelfth is noticed.

8. One section removal: docs/versioning-and-changesets.md's paragraph at line 81, which links to
   ../CONTRIBUTING.md and tells the reader to keep the instruction contract version identical
   across three files. Remove the paragraph, and remove the "Instruction contract version" row
   from the "Two version numbers" table just above it, since the concept does not survive the
   swap. Key the removal on stable text, not a line number.

Every transform must be idempotent: applying it twice produces the same result as applying it
once. Test that explicitly — it is what makes a half-failed setup run safe to re-run.

Done when: npm test and npm run lint pass; scripts/lib/setup.js is still at 100% coverage; every
transform has a test against the real current file content and an idempotency test; no transform
writes to disk; a changeset is recorded.
```

## Iteration 4 — The setup CLI

**Delivers:** `npm run setup`. **Branch:** `feature/setup-cli`

```text
Read docs/downstream-setup-automation.md, sections "Decisions already made" and Iteration 4.
Apply the standing rules in that file.

Baseline first: npm test and npm run lint. Report and stop if not green.

Add scripts/setup.js — a thin CLI over the pure lib in scripts/lib/setup.js, following the same
shape as the existing scripts/register-commands.js and scripts/lib/registration.js split. All
logic worth testing already lives in the lib; this file reads input, applies the plan, and
reports. Add a `setup` script to package.json.

Interface:
  npm run setup                          interactive
  npm run setup -- --name <slug> --yes   unattended, no prompts
  npm run setup -- --dry-run             print the plan, change nothing
  --ai <swap|delete|keep>                what to do with the six instruction files

Order of operations, and it matters:
  1. Refuse to run if the provenance marker already exists, or if the working tree is dirty
     (offer --force for the latter only). State why and exit non-zero.
  2. Print the plan and, unless --yes, require confirmation. --dry-run stops here.
  3. Copy the .template/ payload with placeholders substituted.
  4. Apply the identity rewrites from Iteration 3.
  5. Swap or delete the instruction files.
  6. Copy .dev.vars.example to .dev.vars (never overwrite an existing .dev.vars), then prune.
  7. Apply the prune list and globs.
  8. Write provenance, `git remote add upstream <url>` (skip, with a note, if a remote named
     upstream already exists).
  9. Print the warnings: LICENSE.md still carries the template author's copyright and
     package.json still names them; the four things only a human can do (two Discord
     applications, wrangler secret put per environment, GitHub environments and secrets, the
     Interactions Endpoint URLs); and that `npm run setup:github` exists.
 10. Delete itself last: scripts/setup.js, scripts/lib/setup.js, test/scripts/setup.test.js, and
     the `setup` key in package.json scripts.

Provenance: record the upstream repository, the template version, the template commit SHA, and
the setup date. Put it in package.json under a `template` key rather than a new dotfile, so it
survives and is visible. The date makes output non-deterministic, so the lib function that builds
the provenance object must take the clock as an argument and the tests must pass a fixed value.

A dry run must contact nothing and write nothing — assert that with the same
test/helpers/forbid-fetch.js approach test/contracts/registration.test.js uses for the
registration CLI, spawning the real file as a child process.

Never print a credential. .dev.vars contents are never echoed, not even in --dry-run output.

Done when: npm test and npm run lint pass; a dry run in this repository prints a complete plan and
leaves `git status` clean; the refusal paths (provenance present, dirty tree, invalid slug,
missing --name under --yes) each exit non-zero with a message naming the problem; scripts/lib/ is
still at 100% coverage; a changeset is recorded.
```

```text
remove one entry from the manifest's prune list (show this); the CI job runs setup and a full
green npm test in a fresh copy; a changeset is recorded.
```

## Iteration 6 — `npm run setup:github`

**Delivers:** the GitHub-side structure, applied and then verified against what GitHub actually saved. **Branch:** `feature/setup-github`

```text
Read docs/downstream-setup-automation.md, sections "Decisions already made" and Iteration 6, and
read claude.md's paragraph about GitHub Rulesets and metadata-restriction rule types before you
write anything. Apply the standing rules in that file.

Baseline first: npm test and npm run lint. Report and stop if not green.

Add scripts/setup-github.js plus its pure half in scripts/lib/setup-github.js, and a `setup:github`
script. Unlike scripts/setup.js this one is permanent — re-running it re-verifies GitHub settings —
so it is NOT in the manifest's prune or selfDelete lists.

It shells out to `gh` and creates, idempotently:
  - a `non-prod` environment restricted to the develop branch;
  - a `production` environment restricted to main, with required reviewers enabled;
  - the `DEPLOY_ENABLED` repository variable, set to true, and only with explicit confirmation or
    --enable-deploy, because it is the deployment opt-in;
  - a branch ruleset covering main and develop with exactly the settings tabulated in
    docs/using-this-template.md's "Configure branch protection" section, including the `test`
    required status check.

Then — the part that makes this honest — read back what GitHub saved (`gh api` for the rulesets
and the environments) and print a comparison against what was requested, naming every divergence.
claude.md explains why: an imported ruleset can save with fewer rules than it declares depending
on plan tier, organization policy, and repository visibility. Do not add a `branch_name_pattern`
rule; claude.md says why. If a requested rule did not save, say so plainly and exit non-zero.

It never sets a secret value. It reports which secret NAMES exist per environment
```
